# Project Structure Details

*[한국어](project_structure.md)*

Back to the [main README](../README.md).

```
brands/       Per-brand color-approximation functions (apply_*)
core/         Tone-curve/LUT/stats/validation helpers shared across all brands
datasets/     Committed reference CSVs (official sample metadata, scraped gallery links)
tools/        Analysis (analyze) / download / calibration scripts
models/       Pretrained models used for e.g. face detection
docs/         Detailed documentation (this directory)
```

Unlike `.cube` (a look), this is a colorimetric correction for the color-conversion stage right after RAW demosaic. Lightroom's actual rendering has been confirmed by a real user (Chris Schmauch) |
| `core/icc_export.py` | Writes a standard ICC v4 matrix/TRC profile for Capture One (Base Characteristics → ICC Profile) - `write_icc_matrix_trc_profile`, same matrix data as `dcp_export.py` in a different company's format. 128-byte header + tag table written directly via `struct` (no new dependencies). rXYZ/gXYZ/bXYZ take the chart matrix's rows as-is (opposite direction from DCP - no transpose needed, derivation in the module docstring). Found by testing that a `chad` (identity matrix) tag is required even when wtpt=D50. Independently re-verified via the system littlecms CLI (`transicc`, lcms2 2.19) - unverified on real Capture One. **Added DeviceLink (lut8Type/'mft1') support (2026-09-02)**: `write_icc_devicelink_look_from_lut()` - Capture One doesn't support `.cube` at all (confirmed by research), so this is the alternative path for carrying an arbitrary `brands/*.py` look (HSV saturation/hue shifts etc.) over. The byte layout came from reading littlecms's own source directly (`Type_LUT8_Read`/`Write8bitTables`, github.com/mm2/Little-CMS) since the official ICC spec PDF's text extraction was broken - the R/B axis order (`.cube`'s R-fastest is the opposite of lut8Type's B-fastest) was verified empirically by baking an R/B channel-swap function and round-tripping through transicc. CLAHE can't be captured, same reason as `.cube` (not a pointwise mapping) |
| `core/upscale.py` | Real-ESRGAN (RRDBNet) AI upscaling, supports both PyTorch and ONNX Runtime (`upscale()`) - does not depend on the official `realesrgan`/`basicsr` pip packages (`basicsr` 1.4.2 is broken against current torchvision, confirmed 2026-08); only the RRDBNet architecture itself was ported directly from that source. Weights come from xinntao's official GitHub Release (first-party source, `models/upscale/`, not git-tracked, auto-downloaded on first call); the ONNX engine converts those same weights via `torch.onnx.export()` once and caches the result. Includes tiled inference to handle 100MP-class originals |
| `core/sdcard_undelete.py` | Recovers deleted files from an SD card (FAT32/exFAT) image using filesystem metadata (`recover_fat32`/`recover_exfat`) - more accurate than carving whenever directory entries and cluster chains are still intact. FAT32 loses the first character of the short name on deletion (substituted with `_`); exFAT deletion is logical (only clears the InUse bit in the entry-type byte), so the original filename usually survives intact. Falls back to a "camera files are usually contiguous" heuristic when the cluster chain is broken (e.g. after a quick format) - exFAT recovers even without the FAT table when the NoFatChain flag is set |
| `core/sdcard_carve.py` | Signature-based file carving (PhotoRec-style, `carve()`) - the fallback for files undelete couldn't recover (formatted card, corrupted filesystem). JPEG walks segments and searches for the real EOI after SOS, avoiding the common carving bug of truncating at an EXIF-embedded thumbnail's own EOI; TIFF-based RAW (CR2/NEF/ARW/ORF/RW2/PEF/DNG/3FR/IIQ and most others) estimates the end from the maximum StripOffsets+StripByteCounts across the IFD/SubIFD chain and picks the extension from the Make tag. RAF (Fuji) and CR3 (Canon) are computed precisely - from offsets baked into the RAF header and by summing ISO-BMFF box sizes, respectively - while X3F (Sigma) can only be approximate (`approx=True`) since its directory lives at the end of the file. All formats share a safety net: truncate at the next detected file-start signature if it falls before the estimated end |
