# 근본 원인 규율

## 철칙

```
근본 원인 조사 없이는 어떤 수정도 제안하지 않는다
```

증상만 눌러 끄는 것은 실패다. **급할수록** 이 규율이 더 필요하다 — 추측하고 되돌리는 것보다 체계적으로 파는 게 실제로 더 빠르다.

## 0. 먼저: 이미 풀려 있지 않은가

가장 비싼 코드는 이미 존재하는 코드를 다시 짜는 것이다. **깊게 파기 직전이 확인 시점이다.**

- 이 문제, 다른 브랜치나 최근 커밋에서 이미 고쳐지지 않았는가? (`git log <경로>`)
- 비슷한 걸 하는 함수·모듈이 이미 코드베이스에 있지 않은가?
- 표준 라이브러리나 이미 쓰는 의존성이 이걸 제공하지 않는가?
- 패키지를 재설치하거나 라이브러리 버전을 A/B로 갈아끼우거나 커밋을 거슬러 올라가기 **시작하려는 순간**, 1분을 먼저 쓴다. 이미 있는 해답을 몇 시간에 걸쳐 재발명하는 일은 흔하고, 대개 재발명한 쪽이 설명도 덜 정확하다

## 1. 증상이 아니라 원인 — 조사 단계

**먼저 읽는다.** 에러 메시지와 스택 트레이스를 끝까지 읽는다. 해답이 거기 적혀 있는 경우가 많다. 줄 번호·파일 경로·에러 코드를 흘려보내지 않는다.

**재현한다.** 확실하게 재현되는가? 정확한 절차는? 매번 그런가? 재현이 안 되면 **추측하지 말고 데이터를 더 모은다.**

**최근 변경을 본다.** 무엇이 바뀌어서 이럴 수 있는가? diff, 최근 커밋, 새 의존성, 설정 변경, 환경 차이.

**여러 계층이 얽혀 있으면 계측부터 한다.** (CI → 빌드 → 서명, API → 서비스 → DB 같은 구조)

```
각 컴포넌트 경계마다:
  - 무엇이 들어오는지 찍는다
  - 무엇이 나가는지 찍는다
  - 환경·설정이 실제로 전달되는지 확인한다

한 번 돌려서 "어느 계층에서 끊기는지" 증거를 확보한다
→ 그 계층만 파고든다
```

어디가 깨지는지 모른 채 고치기 시작하면 멀쩡한 계층을 세 번 고치게 된다.

## 1-2. 패턴 분석 — 고치기 전에

- **작동하는 예시를 찾는다.** 같은 코드베이스에서 비슷한데 잘 도는 코드가 있는가?
- 참조 구현이 있다면 **대충 훑지 말고 전부 읽는다**
- **차이를 전부 나열한다.** 아무리 사소해 보여도. "이건 상관없겠지"라고 넘긴 게 원인인 경우가 많다

## 1-3. 가설은 하나씩

- "X가 원인이다, 왜냐하면 Y" 형태로 **명확히** 진술한다. 모호하면 검증할 수 없다
- 가설을 검증할 **가장 작은 변경**을 한다. 한 번에 한 변수만
- 안 되면 → 새 가설을 세운다. **기존 수정 위에 또 수정을 얹지 않는다**
- 모르면 "X를 모르겠다"고 말한다. 아는 척하지 않는다

## 1-4. 증상이 아니라 원인

가장 흔한 실패는 증상만 눌러 끄는 것이다. null 체크를 추가하기 전에 **왜 null이 거기까지 왔는지**를 먼저 묻는다.

- 이 값이 잘못된 상태로 **어디서** 만들어졌는가? 그 지점까지 거슬러 올라간다
- 같은 원인으로 생길 수 있는 **다른 버그**가 이미 잠재해 있지 않은가?
- 방어 코드를 넣는 게 맞는 경우도 있다 — 다만 원인을 알고 나서 내리는 결정이어야 한다

## 2. 추측 대신 증거

코드베이스·라이브러리 동작·에러 원인에 대한 가정은 자주 틀린다. 확인 비용이 싸면 확인한다.

- 이 함수·라이브러리가 실제로 이렇게 동작한다고 **확인**했는가, 그럴 거라고 **가정**했는가?
- 파일을 실제로 읽었는가, 이름만 보고 내용을 짐작했는가?
- "고쳤다", "동작한다"고 말하기 전에 실제로 실행했는가?
- **모든 주장을 검증 가능하게** 한다: 파일명을 대고, 숫자를 보여주고, 실제로 실행한 명령을 인용한다. 뒷받침 못 하는 주장은 모른다고 하는 것보다 나쁘다

## 3. 고친 뒤

- **실패하는 재현 테스트를 먼저** 만들고, 그것이 통과하는 걸로 수정을 증명한다
- 수정은 **하나씩.** "온 김에" 개선이나 리팩터링을 끼워넣지 않는다
- 다른 테스트가 깨지지 않았는지 확인한다

## 4. 세 번 실패하면 구조를 의심한다

수정이 안 통했을 때 시도 횟수를 센다.

- **3회 미만** → 1단계로 돌아가 새로 얻은 정보로 다시 분석한다
- **3회 이상** → 멈춘다. 네 번째 수정을 시도하지 않는다

세 번 넘게 실패했다면 그건 가설이 틀린 게 아니라 **구조가 틀린 것**일 가능성이 높다. 신호는 이렇다:

- 고칠 때마다 다른 자리에서 새 문제가 튀어나온다
- 제대로 고치려면 "대규모 리팩터링"이 필요하다
- 수정이 다른 곳에 새 증상을 만든다

이때는 근본을 묻는다: 이 구조가 애초에 맞는가? 관성으로 붙잡고 있는 건 아닌가? **사람과 상의한 뒤에** 다음 수정을 한다.

## 위험 신호 — 이런 생각이 들면 1단계로

- "일단 빨리 고치고 나중에 조사하자"
- "그냥 X를 바꿔보고 되는지 보자"
- "여러 개 바꿔놓고 테스트 돌리자"
- "테스트는 건너뛰고 수동으로 확인하지"
- "아마 X일 거야, 그거 고치자"
- "완전히 이해는 못 했지만 이러면 될 것 같다"
- 데이터 흐름을 추적하기 전에 해법부터 나열하고 있다
- **이미 2번 이상 실패했는데 "한 번만 더"**

## 사람이 보내는 신호

이런 말이 나오면 접근이 틀렸다는 뜻이다. 멈추고 1단계로 돌아간다.

- "그게 실제로 그런가요?" → 확인 없이 가정했다
- "그러면 그걸 볼 수 있나요?" → 증거 수집을 했어야 했다
- "추측 그만" → 이해 없이 수정을 제안하고 있다
- "다시 생각해봐" → 증상이 아니라 근본을 물어야 한다
- "막힌 건가요?" (답답해하며) → 지금 방식이 안 통하고 있다

## 합리화 차단

| 변명 | 실제 |
|---|---|
| "간단한 문제라 절차까지는" | 간단한 버그에도 근본 원인이 있다. 간단하면 절차도 금방 끝난다 |
| "급해서 절차 밟을 시간이 없다" | 체계적 디버깅이 추측-확인 반복보다 **빠르다** |
| "일단 이것부터 해보고 조사하자" | 첫 수정이 패턴을 정한다. 처음부터 제대로 한다 |
