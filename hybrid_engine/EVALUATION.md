# hybrid_engine 평가 결과 (2026-07)

`evaluation/fidelity.py`(Protocol 1)/`evaluation/cross_camera.py`(Protocol 2)
실측 결과. 재현하려면:

```
python3 -m hybrid_engine.evaluation.fidelity --out eval_reports/fidelity_hasselblad.json
python3 -m hybrid_engine.evaluation.cross_camera --target hasselblad \
    --base-image <아무 인물/풍경 사진> --out eval_reports/generalization_hasselblad.json
```

## Protocol 1: Fidelity (RAW → 공식 렌더러 vs RAW → hybrid_engine)

핫셀블라드 raw+jpeg 13쌍(`raw_calib_cache/`) 전량, `HybridCameraEngine`
기본 profile 기준.

| 지표 | 값 | 해석 |
|---|---|---|
| ΔE00 평균(페어별 평균의 평균) | **15.18** | CIE 기준 "완전히 다른 색"(>10) 구간 |
| ΔE00 P95 평균 | 23.98 | 상위 5% 픽셀은 훨씬 더 나쁨 |
| ΔE00 max 평균 | 58.39 | 페어마다 국소적으로 심하게 틀리는 영역 존재 |
| 그림자(L<33) ΔE00 | 12.52 | |
| 미드톤 ΔE00 | 17.48 | **세 구간 중 가장 나쁨** - 톤커브(블랙/화이트포인트) 문제가 아니라는 신호 |
| 하이라이트(L>66) ΔE00 | 15.97 | |
| SSIM(L채널) 평균 | 0.7409 | 절대 색은 틀려도 대비/구조는 어느 정도 보존(1.0이 완벽 일치) |
| 평균 \|Δhue\| | 34.29도 | 매우 큼 - hue 자체가 크게 어긋남 |

**페어별 편차가 크다**(ΔE00 평균 최저 5.71 ~ 최고 26.79) - 균일한
바이어스가 아니라 장면에 따라 들쭉날쭉하다는 뜻.

### 해석

1. **그림자보다 미드톤이 더 나쁘다는 게 핵심 발견.** 이 프로젝트의
   기존 캘리브레이션 서사(블랙포인트/화이트포인트 맞추기)가 놓치고
   있는 축이 있다는 뜻 - 톤커브를 아무리 정교하게 다듬어도 미드톤
   문제는 못 잡을 가능성이 큼.
2. **Δhue 34도는 매우 크다** - `B1`(학습 LUT)이 톤커브만 손봐서
   ΔE 개선이 미미했던 이유와 정확히 맞아떨어진다. 채도/hue 축이
   병목이라는 진단(README/`hybrid_engine/assets/luts/README.md`에
   이미 기록)이 이 지표로 재확인됨.
3. **SSIM 0.74는 "색은 틀려도 구조는 어느 정도 살아있다"**는 뜻이라
   완전히 무의미한 출력은 아님 - 그러나 절대 색 정확도가 목표라면
   지금 상태로는 부족.

**이 표는 v0.1/v1.1 시점 기록(역사적 맥락 - 아래 여섯 번의 후속 실측을
촉발한 원 데이터)이다. 최신 실측치(v1.2, ΔE00 9.82로 개선)는 맨 아래
"후속 실측 6"과 `assets/profiles/hasselblad.json`의 `_comment` 참고.**

## Protocol 2: Cross-camera generalization (타깃: hasselblad)

소스: fuji(실제 RAW, `raw_calib_cache_fuji/`) + sony/nikon/canon(합성 -
공통 테스트 사진에 `apply_*_look()` 적용, **진짜 카메라 데이터 아님**).

| 소스 | 경로 | 변환 전 b2 | 변환 후 b2 | 변환 전 노이즈σ | 변환 후 노이즈σ |
|---|---|---|---|---|---|
| fuji | 실제 RAW | 42.0 | **58.0** | 1.758 | 2.060 |
| sony | 합성 | 15.0 | 10.0 | 2.253 | 4.408 |
| nikon | 합성 | 19.0 | 10.0 | 2.085 | 4.300 |
| canon | 합성 | 20.0 | 10.0 | 2.043 | 4.334 |

| 요약 지표 | 값 |
|---|---|
| 변환 후 소스 간 b2 표준편차 | 20.78 |
| 변환 후 소스 간 w995 표준편차 | 3.46 |
| 변환 후 소스 간 채도 표준편차 | 23.68 |
| 노이즈 시그니처 소스간 분산(전→후) | 0.178 → 0.991 |
| 지문 소거 비율(post/pre) | **5.57** (1보다 작아야 "소거 성공"인데 오히려 5.57배 커짐) |

### 해석 - 두 가지 실패를 정직하게 인정

1. **합성 소스 3개의 "수렴"(b2 셋 다 정확히 10.0)은 신뢰하면 안 됨.**
   `evaluation/cross_camera.py` docstring에 이미 적어뒀듯, sony/nikon/canon
   합성 소스가 전부 같은 base-image에서 나와서, 브랜드 커브 역산이
   그 브랜드 forward 커브의 거의 정확한 역함수라 다시 같은 사진으로
   되돌아간 뒤 같은 타깃 커브를 맞으니 당연히 수렴한다 - 순환 논증.
   진짜 신호는 **fuji(실제 RAW)가 58.0으로 확 벌어졌다는 것** - 진짜
   다른 카메라/다른 장면이면 전혀 안 수렴한다는 뜻.
2. **지문 소거는 실패했다.** 노이즈 시그니처의 소스 간 분산이 변환
   전(0.178)보다 변환 후(0.991)에 **더 커졌다** - 카메라 고유 렌더링
   특성을 지우기는커녕 오히려 소스 간 차이를 증폭시켰다는 뜻. 다만
   n=4(그것도 3개는 합성)라 통계적으로 약한 신호 - 표본이 더 있어야
   확정적 결론.

## 종합 결론

Protocol 1/2 둘 다 hybrid_engine이 지금 "카메라 렌더링을 정밀하게
재현/일반화한다"는 목표에는 한참 못 미친다는 걸 실측으로 확인했다.
좋은 소식은 병목이 뭔지는 꽤 명확해졌다는 것 - **톤(그림자/하이라이트)
보다 미드톤과 채도/hue 축**. `B1`에서 이미 학습 LUT으로 톤만 손봐서는
개선이 미미했던 것과 이 결과가 일관된다.

**후속 실측(2026-07): 이 문서가 다음 후보로 제안했던 "a/b(채도/hue)
채널 학습 기반 보정"을 실제로 시도했고, 역시 기각됐다.** hue만 따로
학습 LUT으로 보정해도 ΔE 개선은 +2.1%(톤 LUT의 +4.9%보다도 작음) -
자세한 수치와 분석은 `hybrid_engine/assets/luts/README.md` 참고. 톤도
hue도 **개별 축을 1D LUT으로 고치는 접근 자체**가 5% 미만 개선에서
막힌다는 게 이제 두 번 확인됐다는 게 핵심 - "미드톤+hue가 병목"이라는
진단은 맞지만, 그걸 채널별로 독립적으로 고치면 안 풀린다는 뜻이다.
잔차가 L/a/b 결합(joint) 형태일 가능성이 높아서, 다음 후보는 개별
축 LUT이 아니라 **3D 잔차 LUT**이나 Phase 2(공간 연산)다.

**후속 실측 2(2026-07): 3D 잔차 LUT(9^3 격자, L/a/b 결합)도 시도했고,
더 명확하게 기각됐다.** in-sample ΔE는 +11.1%로 지금까지 셋 중 가장
좋아 보였지만, 13-fold leave-one-out 교차검증에서는 **-5.7%(기준선보다
오히려 나빠짐)**로 뒤집혔다 - 729개 격자점을 13장에서 학습하는 건
사실상 암기라 안 본 이미지엔 일반화가 안 된다는 뜻. 자세한 수치는
`hybrid_engine/assets/luts/README.md` 참고. "톤/hue를 각각 고치면
5% 미만"이라는 진단 자체는 여전히 유효하지만, "그러니 조합으로
학습하자"는 지금 표본(13장)으로는 통하지 않는 해법이었다 - 표본이
훨씬 늘어나거나(이슈 #4의 X2D II 데이터), 정규화된 더 성긴 격자로
재시도하기 전까진 Phase 2(공간 연산)나 raw 베이스라인 특성화 쪽이
더 현실적인 다음 후보.

**후속 실측 3(2026-07): "격자가 너무 크면 과적합"이라는 가설을 검증하려고
더 작은 2D 잔차 LUT(a/b만, 81격자)도 시도했다 - 역시 기각.** in-sample
+1.4%, leave-one-out 교차검증 **-2.7%**(729→81로 10분의 1 넘게
줄였는데도 여전히 마이너스). 톤(1D)→hue(1D)→3D(joint)→2D(joint, 더
작은 격자) 네 번의 실험이 전부 기각으로 수렴한 지금, **격자/LUT
계열 접근 자체가 표본 13장 규모에서는 막다른 길**이라고 결론짓는 게
맞다. 자세한 비교표는 `hybrid_engine/assets/luts/README.md` 참고.
다음은 LUT을 더 정교하게 만드는 게 아니라 표본을 늘리거나(이슈 #4)
접근 자체를 바꾸는(Phase 2 공간 연산, raw 베이스라인 특성화) 쪽으로
방향을 틀어야 함.

**후속 실측 4(2026-07): Phase 2(로컬 콘트라스트, L채널 언샤프 마스크)를
시도했다 - 결과는 기각도 채택도 아닌 "무신호(null result)".**
`calibrate_profile.py --mode spatial`이 spatial_radius/amount/threshold
3개를 좌표하강으로 찾았는데:

- 공간 연산 보정 전 ΔE(기준선): 14.85
- 공간 연산 보정 후 ΔE (in-sample): 14.84 (**+0.0%** - 사실상 무보정에 수렴)
- 공간 연산 보정 후 ΔE (4-fold 교차검증): 14.55 (+2.0%)

찾아낸 최적 파라미터 자체가 amount=0.1(탐색 후보 중 최솟값에 가까움)로
수렴했다는 게 핵심 신호 - **좌표하강이 "효과가 거의 없는 게 최선"이라고
판단했다는 뜻.** LUT 실험들과 달리 in-sample보다 교차검증이 더 좋게
나온 것도(+0.0% → +2.0%) 진짜 효과가 아니라 폴드 4개짜리 표본 변동
범위 안의 노이즈로 해석하는 게 맞다 - 실제 효과가 있었다면 in-sample이
교차검증보다 낮게 나올 이유가 없다. **채택 안 함.** 톤/hue/2D/3D LUT
넷의 명확한 음성 결과와 달리 이건 "이 파라미터화로는 신호를 못
찾았다"는 약한 결론이라, Phase 2 자체를 완전히 접기보다는 다른
공간 연산(선명화 반경을 더 세밀하게, 혹은 블루밍/광훈 같은 다른
효과)이나 issue #4의 X2D II 데이터로 표본이 늘어난 뒤 재탐색할
여지는 남겨둔다. `hasselblad.json`은 계속 use_spatial=False로 미변경.

**다섯 번의 실험(톤/hue/3D/2D/공간) 전부가 표본 13장으로는 눈에 띄는
개선을 못 찾았다는 것 자체가 이제 이 프로젝트의 실측 결론이다** - 이
데이터 규모에서 hybrid_engine의 ΔE≈15 병목을 학습 기반으로 뚫는 건
막혀 있고, 남은 현실적인 경로는 (1) 이슈 #4의 X2D II 실측 데이터로
표본을 실질적으로 늘리거나, (2) raw 베이스라인 자체(libraw 렌더링과
Phocus/카메라 엔진의 차이)를 색차트로 특성화해서 지금 측정 중인
"엔진 대 엔진" 차이에서 "raw 디코드 대 raw 디코드" 차이를 분리해내는
것.

**후속 실측 5(2026-07, GitHub 이슈 #4 대응): raw 베이스라인 특성화 -
이번엔 진짜 신호를 찾았다.** `calibrate_profile.py --mode raw_baseline`이
hybrid_engine의 Phase 0-2를 전혀 거치지 않은 순수 rawpy 디코드에 전역
3x3 선형 컬러 매트릭스 하나만 최소자승으로 맞춰서 비교했다:

| 방법 | ΔE(CIEDE2000) |
|---|---|
| hybrid_engine 현재(파라메트릭 profile) | 14.85 |
| **raw 디코드 자체(무보정)** | **11.78** |
| 3x3 매트릭스 보정 (in-sample) | 8.55 |
| **3x3 매트릭스 보정 (4-fold 교차검증)** | **10.01** |

**핵심 발견 두 가지:**

1. **아무 보정도 안 한 raw 디코드(11.78)가 hybrid_engine의 정교한
   톤/채도 파이프라인을 거친 결과(14.85)보다 ΔE가 더 낮다.** 즉 지금
   hybrid_engine의 Phase 1(tone_core/color_core, v1.1에서 좌표하강으로
   "캘리브레이션"됐다고 여겼던 그 파라미터들)이 색을 실측 타깃에 더
   가깝게 만드는 게 아니라 **오히려 더 멀어지게 만들고 있다.**
   좌표하강이 13장의 ΔE 평균을 최소화하도록 맞춘 결과가 맞는데도
   무보정보다 나쁘다는 건, 애초에 tone_core/color_core의 함수 형태
   (S커브/가우시안 채도 부스트) 자체가 이 문제에 안 맞는 모양이라는
   뜻일 가능성이 높다.
2. **색차트 없이도 전역 3x3 행렬 하나면 교차검증 기준 32.6% 개선
   (14.85→10.01)이 나온다.** 이건 지금까지 시도한 다섯 실험(톤/hue/
   3D/2D/공간 LUT) 중 유일하게 사전 채택 기준(>20% 개선)을 명확히
   넘긴, 그것도 교차검증으로 확인된 결과다. 페어 13장이라는 같은
   표본으로 다른 LUT들은 다 실패했는데 이건 성공했다는 게 흥미로운데,
   자유도가 9개(3x3 행렬)뿐이라 톤 LUT(256)/2D(81×2)/3D(729×3)보다
   훨씬 적어서 과적합이 근본적으로 덜 되는 게 이유로 보인다.

**의미: 지금까지 다섯 실험은 전부 "이미 계산된 hybrid_engine 파이프라인
결과 위에 추가 보정을 얹는" 방식이었는데, 이 실측은 그 파이프라인
자체(특히 Phase 1의 함수 형태)가 문제의 근원일 수 있다는 걸 보여준다.**
`hasselblad.json`은 이 발견만으로 아직 바꾸지 않았다 - 3x3 매트릭스를
어디에 어떻게 통합할지(Phase 0/1을 대체할지, 그 앞에 추가할지, tone_core/
color_core 파라미터를 이 매트릭스 기준으로 다시 캘리브레이션할지)는
설계 결정이 필요해서 별도 논의 후 진행.

**후속 실측 6(2026-07): 매트릭스를 실제 파이프라인에 통합 - 처음엔
실패했지만, 원인을 찾아 고치고 나니 성공했다.** 사용자 지시대로
tone_core/color_core를 삭제하지 않고 재배치했다: **Phase 0 = raw_baseline
매트릭스, Phase 1 = tone_core 재학습, Phase 2 = color_core 재학습**
(`calibrate_profile.py --mode raw_baseline_pipeline`, `pipeline/engine.py`).

1차 시도(그대로 통합)는 실패했다 - 4-fold 교차검증 ΔE 14.852(기존
14.847과 사실상 동일, **+0.0%**). 후속 실측 5의 단독 매트릭스 32.6%가
파이프라인에 넣자마자 사라진 것. 원인을 진단 스크립트로 격리했다:

| 조합 | ΔE |
|---|---|
| 매트릭스만(단독 실험과 동일) | 8.55 |

등 원래 유채색인 피사체)을 색치우침 추정에서 제외하는 robust 변형을
구현하고(`gray_world_saturation_percentile` profile 파라미터, 기본값
100.0 = 기존 동작과 동일), `calibrate_profile.py --mode gray_world`로
후보 격자 [30, 50, 70, 85, 100]을 13쌍 전체에서 탐색했다. 이
파라미터는 페어별 손실이 독립이라 leave-one-out 교차검증을 손실 행렬
한 번으로 정확하게 계산할 수 있다.

| percentile | 13쌍 평균 ΔE00 | 야경 페어(B0001395) 단독 |
|---|---|---|
| 30 | 10.168 | 21.316 |
| 50 | 9.876 | 20.089 |
| 70 | 9.704 | 18.146 |
| 85 | 9.699 | 18.146 |
| **100(기존)** | **9.687** | **18.146** |

in-sample조차 100(기존 동작)이 최선이고, 백분위를 낮출수록 단조적으로
나빠진다. LOO 교차검증은 10.015(-3.4%)로 더 나쁘다(70과 100 사이 미세한
동률 근처에서 fold별 선택이 흔들리는 비용). 결정적인 건 **이 수정이
겨냥했던 야경 페어 자체가 개선은커녕 percentile=30에서 +3.2 더
나빠진다**는 것.

왜 그런가: 후속 실측 10의 진단(전역 색치우침 추정이 하늘까지
과보정한다)은 하늘 영역의 국소 오차 메커니즘으로는 실측 그대로
맞지만, 화면의 다수를 차지하는 나머지 영역(도로/건물/궤적)은 오히려
그 "오염된" 전역 추정에 의해 실제 카메라 JPEG와 가까운 방향으로
보정되고 있었다. 채도 높은 픽셀을 추정에서 빼면 색치우침 추정이
중성 쪽으로 이동해 보정량이 줄고, 하늘의 국소 개선폭보다 다수
영역의 악화폭이 커서 페어 전체 ΔE는 나빠진다. 또한 v1.2의 tone/color
파라미터 자체가 기존(full) gray world를 전제로 좌표하강 튜닝된 것도
한몫한다. 요컨대 **야경 하늘 문제는 전역 색치우침 추정기를 어떻게
바꿔도 해결되지 않는, 본질적으로 공간적(per-region) 문제**다 - 전역
스칼라 하나로는 하늘과 도로를 동시에 만족시킬 수 없다.

`gray_world_saturation_percentile` 파라미터와 단위 테스트는 코드에
남긴다(기본값 100.0이라 배포 동작 변화 없음) - 실험 재현과 후속
연구용. `hasselblad.json`은 변경 없음.

**후속 실측 12(2026-07-20): 후속 실측 10의 ② 가설(피부톤 hue 대역
국소 chroma 보정)도 실측했다 - 기각.** `hue_core.py`에 `apply_hue_chroma_lut`
(hue는 유지하고 chroma만 hue별로 배율 조정 - 기존 hue 회전 LUT과
축이 분리된 자매 함수)을 새로 만들고, `calibrate_profile.py --mode
hue_chroma`로 13쌍에서 순환 36-bin LUT을 학습했다(bin별 배율은
"sum(타깃 chroma)/sum(소스 chroma)" 에너지 비율로 추정 - 픽셀별 비율
평균은 소스 chroma가 0에 가까우면 발산해서 못 씀).

- hue-chroma 보정 전 ΔE(v1.2 기준선): 9.687
- hue-chroma 보정 후 ΔE (in-sample): 9.877 (**-2.0%**)
- hue-chroma 보정 후 ΔE (leave-one-out 교차검증, 13-fold): 10.078 (**-4.0%**)

**채택 안 함 - 이번엔 in-sample부터 이미 마이너스다.** 지금까지의
LUT 실험(3D/2D/hue 재시도) 전부 in-sample은 양성이었다가 교차검증에서
무너지는 패턴이었는데, 이건 그 단계조차 못 넘었다. 원인으로 의심되는
건 페어 간 평균 밝기/채도 스프레드(후속 실측 6에서 확인된 노출
10배 차이와 같은 문제) - 13장을 그대로 pooling해서 에너지 비율을
추정하면 특정 hue bin의 배율이 소수의 극단적인 페어(노출이 유난히
높거나 낮은 페어)에 의해 왜곡될 수 있다. 결과적으로 후속 실측 10에서
짚은 두 가설(① Gray World 과보정, ② hue별 chroma 국소 보정) 모두
직접 검증해봤고 둘 다 이 데이터셋 규모에서는 기각됐다 - v1.2의 남은
잔차(미드톤, 옐로우오렌지/블루 hue 대역)는 지금까지 시도한 어떤
방식으로도 아직 못 줄였다는 뜻. `learned_hue_chroma_lut` 파라미터와
테스트는 코드에 남긴다(기본값 None이라 배포 동작 변화 없음).
`hasselblad.json`은 변경 없음.

**후속 실측 13(2026-07-20): "Gray World를 그냥 없애고 다시 만들자"는
제안을 실측했다 - 완전 제거는 대참사, 밝기 구간별(zoned) 재설계도
기각.** 지금까지 세 번(후속 실측 11 percentile-robust, 12 hue-chroma,
그리고 이번 zoned) 전부 "Gray World를 고치거나 보완"하는 방향이었는데,
이번엔 근본 질문 자체("애초에 Gray World가 필요한가?")부터 실측했다.

**1) Gray World를 완전히 제거(`correct_color_cast=False`)하면 어떻게
되는가** - camera_whitebalance 기반 `unify_to_d65`(Phase 0)만으로
색치우침 보정이 충분한지 테스트:

| | 13쌍 평균 ΔE00 |
|---|---|
| Gray World 있음(기존, v1.2) | 9.687 |
| **Gray World 없음** | **18.431 (거의 2배 악화)** |

13쌍 전부 예외 없이 나빠졌다(제일 좋았던 페어도 2.49 -> 24.29로 붕괴).
심지어 고치려던 야경 페어도 18.15 -> 23.90으로 오히려 더 나빠졌다 -
카메라 자체 WB 메타데이터는 촬영 당시 광원에 대한 색순응만 처리하고,
그 이후 남는 카메라/매트릭스 고유의 잔차 색치우침은 Gray World가
전담하고 있었다는 뜻. **완전 제거는 명백히 답이 아니다.**

**2) 그래서 "다시 만들자"는 제안대로 밝기 구간별(zoned) Gray World를
새로 설계했다** - `gray_world_normalize_zoned()`(`core/normalizer.py`):
전역 스칼라 하나 대신, 이미지 자체의 luma 퍼센타일로 나눈 n개 밝기
구간마다 독립적으로 Gray World를 추정하고 가우시안 가중으로 부드럽게
섞는다(경계 밴딩 방지). 하늘(밝음)과 도로/광원(어두움)이 서로 다른
색치우침 추정을 받을 수 있게 하는 게 목적. `gray_world_zones` profile
파라미터로 노출(`--mode gray_world_zoned`), 후보 [1,2,3,4,5]를 13쌍
전체에서 탐색:

| zones | 13쌍 평균 ΔE00 |
|---|---|
| **1(기존, 기준선)** | **9.687** |
| 2 | 10.312 |
| 3 | 10.228 |
| 4 | 10.197 |
| 5 | 10.191 |

in-sample조차 zones=1이 최선이고, **leave-one-out 교차검증 13-fold
전부 예외 없이 zones=1을 선택**했다(기준선 그대로, +0.0%) - zones를
늘릴수록 무조건 나빠지는 단조 패턴이라 더 세분화해도 반전될 여지가
없다. 왜 그런가: 밝기 구간을 나눠서 국소적으로 더 정확하게 추정해도,
각 구간이 참조할 수 있는 픽셀 수가 줄어들어(구간이 늘수록 표본이
쪼개짐) 추정 자체가 불안정해지고, 야경 같은 극단적 케이스가 아닌
나머지 12쌍(색치우침이 밝기와 별로 안 엮여 있는 정상적인 장면들)에서는
오히려 전역 추정보다 노이즈만 늘어난다.

**세 번의 시도(percentile-robust, hue-chroma, zoned) 모두 같은 결론으로
수렴한다: Gray World의 "전역 스칼라"라는 단순함 자체가 이 13장짜리
데이터셋에서는 강점이다(자유도가 낮아 과적합이 안 됨) - 더 정교하게
만들려는 시도는 방향이 맞아도(야경 하늘 진단은 여전히 유효) 표본
크기 앞에서 전부 무너진다.** 진짜 공간적으로 다른 처리가 필요한
문제(픽셀 위치/영역별 로컬 화이트밸런스)를 13장으로 학습하는 건
근본적으로 무리라는 뜻 - 이슈 #4의 X2D 데이터로 표본이 실질적으로
늘기 전까지는 이 축을 더 파는 게 비생산적이라고 판단한다.
`gray_world_zones` 파라미터/테스트는 코드에 남기고(기본값 1, 배포
동작 무변화), `hasselblad.json`은 변경 없음.

**후속 실측 14(2026-07-20): "그레이 월드 미세보정"을 실측했다 - 신호
없음(사실상 무승부).** 후속 실측 11/12/13이 전부 자유도를 늘리는
방향이었다가 기각된 것과 정반대로, 이번엔 자유도를 최대한 줄여봤다 -
`gray_world_strength`(추정된 색치우침 스케일을 항등과 선형 보간하는
배율 하나, `core/normalizer.py`): 1.0이 기존 동작, 0.0이 완전
제거(후속 실측 13의 대참사와 동일), 그 사이/바깥 값도 허용. 자유도
딱 1개라 지금까지 시도한 것 중 가장 보수적인 조정.

`--mode gray_world_strength`로 [0.6, 0.7, ..., 1.4] 13개 후보를 13쌍
전체에서 촘촘하게 탐색:

| strength | 13쌍 평균 ΔE00 |
|---|---|
| 0.60 | 12.781 |
| 0.80 | 10.632 |
| 0.90 | 9.839 |
| 0.95 | 9.623 |
| **1.00(기존, 기준선)** | **9.687** |
| 1.05 | 10.091 |
| 1.20 | 11.959 |
| 1.40 | 14.696 |

곡선이 1.0 근처에서 뚜렷한 U자형이고(강도를 올리든 내리든 확실히
나빠짐), in-sample 최선은 strength=0.95로 아주 살짝 개선(9.687 ->
9.623, +0.7%) - 13-fold LOO 중 12개가 0.95를 선택했다. 하지만
**leave-one-out 교차검증은 9.689(기준선보다 -0.0%, 사실상 동일)** -
in-sample의 미미한 개선조차 교차검증에서 노이즈 수준으로 사라진다.
페어별로 봐도 방향이 섞여 있다(pair 0/1/3/6/8/9/11은 개선, pair
2/4/7/10/12는 악화) - 일관된 신호가 아니라 우연에 가깝다.

**결론: 자유도를 1개까지 줄여도 신호가 없다.** percentile-robust(11)/
hue-chroma(12)/zoned(13)은 전부 명확하게 음성(기준선보다 나쁨)이었고,
이번 strength(14)는 유일하게 "나쁘지도 좋지도 않은" 결과 - 그런데도
채택 기준(의미 있는 교차검증 개선)에는 못 미친다. 네 번의 서로 다른
축(어떤 픽셀을 쓸지/hue별 배율/공간 구간/강도)을 전부 시도해본 뒤
내리는 최종 판단: **v1.2의 Gray World 단계는 이 13장짜리 데이터셋에서
이미 사실상 최적점에 있다** - 야경 하늘 과보정은 진단대로 실재하는
한계지만, 이 표본 규모로는 그 어떤 방향의 조정으로도 고칠 수 없다.
`gray_world_strength` 파라미터/테스트는 코드에 남기고(기본값 1.0,
배포 동작 무변화), `hasselblad.json`은 변경 없음 - 이 축은 이슈 #4의
X2D 데이터가 실질적으로 늘기 전까지 더 파지 않기로 한다.

**후속 실측 15(2026-07-20): Phase 0 내부 단계 순서를 바꿔봤다 - 지금
순서가 이미 최선임을 처음으로 실측 검증.** `engine.py`의 처리 순서
(매트릭스 → 카메라 WB 통일(D65 색순응) → Gray World → LAB 분리 →
tone → color)는 지금까지 "논리적으로 이렇게 하는 게 맞겠지"로 정해진
것이었지 실측으로 검증된 적이 없었다. v1.2 파라미터 그대로 두고
개별 함수(`raw_baseline.apply_color_matrix`/`color_matrix.unify_to_d65`/
`normalizer.gray_world_normalize`/`tone_core.apply_tone`/`color_core.apply_color`)
를 직접 다른 순서로 조합해서 13쌍 in-sample로 비교(탐색적, 교차검증
전 단계):

| 순서 | ΔE00 |
|---|---|
| **기준선(매트릭스→WB통일→GrayWorld→tone→color)** | **9.687** |
| WB통일↔GrayWorld 교체(매트릭스→GrayWorld→WB통일) | 19.932(+106%) |
| 매트릭스↔WB통일 교체(WB통일→매트릭스→GrayWorld) | 10.222(+5.5%) |
| GrayWorld를 제일 먼저(GrayWorld→매트릭스→WB통일) | 20.324(+110%) |
| tone↔color 교체(color→tone) | 9.683(거의 동일) |

**WB통일이 Gray World보다 먼저 와야 한다는 게 결정적으로 중요하다** -
순서만 바꿔도 오차가 거의 2배(9.7 -> 20 안팎)로 뛴다. 원인 추정: 카메라
WB 통일은 `camera_whitebalance`(EXIF/RAW 메타데이터)를 기준으로 촬영
당시 광원을 추정해서 D65로 색순응시키는 단계인데, 이게 정확히 작동하려면
입력이 "raw 그대로의" 색치우침을 담고 있어야 한다. Gray World가 먼저
픽셀 통계로 색을 이미 평탄화해버리면 그 뒤에 오는 WB통일이 이미
왜곡된 입력을 광원 추정에 써서 이중보정/충돌을 일으키는 것으로 보인다.
매트릭스↔WB통일 순서도 지금 순서(매트릭스 먼저)가 더 낫다(+5.5%,
치명적이진 않지만 방향은 명확). 반대로 tone↔color 순서는 사실상
무관하다(9.683 vs 9.687) - color_core의 L 가중치가 tone 적용 전/후
어느 쪽 L을 받든 실질적 차이가 거의 없다는 뜻.

**코드는 안 바꿈** - 지금 배포된 순서가 테스트한 5가지 중 이미 최선이라
바꿀 이유가 없다. 다만 지금까지 암묵적으로 "당연히 이 순서"였던 설계
결정이 처음으로 정량적 근거를 갖게 됐다는 점에서 기록해둘 가치가
있다고 판단. 교차검증까지는 안 했음(순서는 학습되는 파라미터가 아니라
이산적 구조 선택이라 과적합 위험이 없어서, 13쌍 in-sample 비교로도
충분히 결론 낼 수 있다고 판단 - 다른 실험들과 달리 "이 표본에만 맞는
우연"일 가능성이 낮은 종류의 결과).

**후속 실측 16(2026-07-21): X2D II ColorChecker 페어(9장)를 X1D 13장과
합쳐 22쌍으로 재학습 - 원래 13쌍 벤치마크에서 미미하지만 처음으로 실제
개선(-1.3%), 그 위에 톤/hue LUT을 다시 얹어봐도(n=13에서 과적합으로

자체가 가능했다(`load_image_linear(..., resize_to=...)`로 정수 상태에서

`raw_calib_cache/`의 X1D 13쌍 + `datasets/hasselblad/.../kmichels-x2dii-2026-07/`의

매트릭스+파라메트릭 톤/채도를 처음부터 재학습(`recalibrate.py
--cache-dir`):

| 비교 | ΔE00 |
|---|---|
| 기존 v1.2, 22쌍 기준(챠트 포함이라 원래 9.687보다 높게 나옴) | 11.548 |
| 22쌍으로 재학습, 4-fold 교차검증(같은 22쌍 기준) | 10.491 (+9.2%) |

이 9.2%는 "챠트가 섞인 더 어려운 기준선 대비"라 액면 그대로 못 믿는다 -
**원래 13쌍 벤치마크로 직접 비교**해야 공정하다:

| 프로필 | 원래 13쌍(X1D)에서 ΔE00 |
|---|---|
| 기존 v1.2 | 9.573(in-sample - 공식 9.687 교차검증 수치와 근접) |
| 22쌍으로 재학습한 프로필 | 9.448 |
| 차이 | -1.3% |

작지만 방향은 처음으로 "챠트 데이터를 섞어도 원래 벤치마크가 나빠지지
않고 오히려 살짝 좋아진다"는 긍정적 신호 - 지금까지 이 프로젝트에서
시도한 축 중 유일하게 순수 잡음이 아닌 쪽으로 기운 경우다. 다만
recalibrate.py의 배포 기준(교차검증 5% 이상 개선)에는 한참 못 미쳐서
`hasselblad.json`은 바꾸지 않는다.

이 김에 n=13에서 "과적합 위험 때문에" 기각됐던 학습 LUT 두 축(후속
실측에 정식 번호는 안 붙었지만 톤 LUT/hue LUT 둘 다 초기 V0.1 문서에서
과적합 우려로 파라메트릭을 택함)을 n=22 pooled 세트로 다시
4-fold nested CV(매트릭스+파라미터+LUT을 폴드마다 전부 그 폴드의
학습데이터로만 재학습):

| 축 | 교차검증 ΔE00 | 변화 |
|---|---|---|
| 매트릭스+파라메트릭만(LUT 없음) | 10.491 | 기준 |
| + 학습 톤 LUT(32bin) | 10.512 | -0.2%(잡음) |
| + 학습 hue LUT(36bin) | 10.405 | +0.8%(약한 양성, 폴드 4개 중 3개는 개선/1개는 악화 - 방향은 있지만 결정적이진 않음) |

톤 LUT은 n을 거의 두 배로 늘려도 여전히 신호가 없다 - 과적합이 아니라
애초에 "매끄러운 파라메트릭 커브로 이미 거의 다 잡힌다"는 뜻일 가능성이
높다. hue LUT은 미약하게나마 처음으로 0을 넘는 방향을 봤지만(+0.8%),
크기가 지금까지 기각해온 다른 실험들(예: 그레이 월드 strength +0.7%
in-sample/0% CV)과 같은 잡음 수준이라 단독으로 배포 근거가 되진 않는다.

**LUT을 여러 개 동시에 얹으면(스태킹) 오히려 확실히 나빠진다**는 것도
같은 실험에서 확인: hue+lab2d 동시 적용 CV ΔE 10.986(기준 대비 -4.7%,
즉 더 나쁨), hue+lab2d+lab3d 풀스택은 11.898(-13.4%, 훨씬 더 나쁨).
LUT들이 서로 독립적인 잔차를 보정하는 게 아니라 겹쳐서 이중보정/노이즈
증폭을 일으킨다는 뜻 - `assets/luts/README.md`에 이미 기록된 "잔차가
채널별로 안 나뉜다" 가설과 일치하는 추가 증거.

**pooled 실험을 다시 봤더니 챠트 버스트 9장을 통째로 넣은 게 오히려
손해였다.** 같은 챠트를 94초 안에 10번 찍은 프레임들은 최소자승 적합
에서 사실상 "9배 가중치"로 작용해서 매트릭스를 챠트 쪽으로 과도하게
끌어당긴다는 가설을 세우고, 챠트를 대표 프레임 1~2장으로 줄여서
재시도(원래 13쌍 X1D 벤치마크로 직접 평가, in-sample):

| 챠트 개수 | 원래 13쌍(X1D)에서 ΔE00 |
|---|---|
| 0장(기존 v1.2) | 9.573 |
| 1장 | 9.376(-2.1%) |
| 2장 | 9.332(-2.5%) |
| 9장(전체 버스트) | 9.448(-1.3%) |

가설대로 9장 전체보다 1~2장이 더 낫다 - 다만 위 표는 전부 그 13쌍이
학습에도 쓰인 in-sample 수치라 공정한 비교가 아니다. **13쌍 각각을
진짜 held-out으로 두고(나머지 12쌍 X1D + 챠트 2장으로 학습 -> 안 본
1쌍 평가) 13-fold LOO로 다시 검증**:

| 학습 구성 | LOO ΔE00(13-fold) |
|---|---|
| X1D 12쌍만(현재 절차와 동등) | 9.963 |
| X1D 12쌍 + 챠트 2장 | 9.598 (**+3.7%**) |

13개 폴드 중 10개가 개선 또는 사실상 동일, 2개만 미세하게 악화
(5.035→5.036, 12.231→12.241 - 잡음 수준) - **이번 세션에서 나온 것 중
가장 견고하게 검증된 양성 신호**다. 그래도 recalibrate.py의 배포
기준(5%)에는 아직 못 미치고, 원래 데이터셋(13쌍)만으로 잰
`hasselblad.json`을 이 15쌍(13+챠트2) 기준으로 그냥 덮어쓰면 비교
기준 자체가 달라져서 "9.687"이라는 숫자의 의미가 바뀐다 - 그래서
`hasselblad.json`은 이번에도 바꾸지 않되, 챠트 2장을 정식으로
`raw_calib_cache/`에 포함시킬지는 별도 결정으로 남겨둔다.

**종합**: 이번 세션에서 시도한 축(그레이 월드 4종, hue-chroma LUT,
파이프라인 순서, pooled 데이터셋의 여러 변형, LUT 스태킹, 챠트 개수별
dedup)까지 합치면 지금까지 이 프로젝트가 시도한 독립적인 축이 15개를
넘는다. 가장 잘 검증된 결과(챠트 2장 LOO CV, +3.7%)조차 목표로 삼은
"9→7"(약 -27% 필요)에는 한참 못 미친다. 원인은 아키텍처 자체의 한계로
보인다 - 카메라 JPEG 렌더링은 장면별 비선형 처리(하이라이트 복원,
로컬 톤매핑, 샤프닝/노이즈리덕션이 색에 미치는 간접효과)를 포함하는데,
전역 3x3 매트릭스+매끄러운 톤/채도 커브 + 저차원 LUT로는 구조적으로
못 잡는 오차가 남는다. 여기서 더 줄이려면 (a) 실제로 다양한 장면(현재
X2D 데이터는 전부 같은 챠트 버스트라 "다양한 장면"이 아님 - 이슈 #4
3번 항목이 요청한 것과 다름)의 raw+jpeg 페어가 지금보다 훨씬(수십 장
단위로) 더 필요하거나, (b) 파라메트릭/LUT 혼합이 아니라 정칙화가 강한
학습 기반 톤매핑(예: 작은 신경망)처럼 근본적으로 다른 모델이 필요할
가능성이 높다 - 둘 다 지금 가진 데이터/아키텍처로는 이번 세션 안에서
해결할 수 없는 범위.

**후속 실측 17(2026-07-22): Gray World 대신 다른 고전 색치우침 추정
알고리즘을 시도 - Gray Edge가 뚜렷한 승자.** Gray World("화면 평균이
무채색"), White Patch("가장 밝은 픽셀이 흰색"), Shades of Gray(둘을
잇는 Minkowski p-norm 일반화), Gray Edge("픽셀값이 아니라 공간 미분/
엣지의 평균이 무채색") 넷을 `calibrate_profile.py --mode
color_cast_algorithm`으로 비교(매트릭스/톤/채도는 shipped v1.2 그대로,
색치우침 알고리즘만 교체, 13쌍 X1D, LOO 교차검증):

| 알고리즘 | LOO 교차검증 ΔE00 | 변화 |
|---|---|---|
| Gray World(기준) | 9.573 | - |
| White Patch(percentile=100) | 11.345 | -18.5%(명확히 나쁨) |
| Shades of Gray(p=20) | 9.388 | +1.9%(약한 양성) |
| **Gray Edge(p=1)** | **9.368** | **+2.1%** |

White Patch는 핫셀블라드 사진에서 "가장 밝은 지점=흰색" 가정이 잘 안
맞는다는 뜻(반사광/조명 자체가 유채색인 경우가 많은 듯). Gray Edge는
유일하게 픽셀 강도가 아니라 공간 미분(엣지)을 쓰는 알고리즘인데 가장
좋았다 - LOO 폴드 13개 중 거의 전부(11/13)가 p=1(스무딩 없는 1차
미분)을 선택할 만큼 일관됨. `normalizer.py`에 `white_patch_normalize`/
`shades_of_gray_normalize`/`gray_edge_normalize` 세 함수와 `normalize()`의
`color_cast_algorithm` 선택 파라미터로 구현(기본값은 `"gray_world"`라
기존 동작/`hasselblad.json`은 이 커밋만으로는 안 바뀜).

**후속 실측 18(2026-07-22): Gray Edge(후속 실측 17) + 챠트 pooling(후속
실측 16)을 매트릭스부터 같이 재학습하니 개별 효과의 합보다 훨씬 큰
+11.1%가 나왔다 - 이 프로젝트의 5% 배포 기준을 처음으로 명확히 넘겨서
`hasselblad.json`을 v1.3으로 갱신했다.** 후속 실측 17은 매트릭스/톤/채도를
shipped 그대로 두고 알고리즘만 바꿨는데, 이번엔 `color_cast_algorithm=
gray_edge`로 고정한 채로 매트릭스(최소자승)부터 톤/채도(좌표하강)까지
전부 그 설정에 맞춰 처음부터 재학습했다 - Gray Edge가 만들어내는 색
분포가 Gray World와 다르니, 그 위에서 매트릭스/커브도 다시 최적화해야
진짜 잠재력이 나온다는 가설. 13-fold LOO(원래 X1D 13쌍 기준, 학습셋에는
항상 챠트 2장 포함):

| 조합 | LOO 교차검증 ΔE00 | 변화 |
|---|---|---|
| 기준(Gray World, X1D 13쌍만, 매트릭스/톤/채도 재학습) | 9.963 | - |
| Gray Edge만(X1D 13쌍만) | 9.024 | +9.4% |
| 챠트 pooling만(Gray World, X1D+챠트2) | 9.598 | +3.7% |
| **Gray Edge + 챠트 pooling** | **8.859** | **+11.1%** |

개별 효과(9.4%, 3.7%)를 단순히 더한 것보다도 큰 시너지(11.1%)가 나온
게 흥미롭다 - 매트릭스를 Gray Edge 전제로 재학습하면서 챠트 데이터가
주는 색 다양성을 더 잘 활용하게 된 것으로 추정(챠트는 ColorChecker라
넓은 색역을 커버해서, Gray Edge 위에서 매트릭스가 그 다양성으로부터
더 정확하게 적합될 여지가 큼).

**배포 결정**: 15쌍 전체(X1D 13 + 챠트 2)로 최종 매트릭스+톤/채도를
재학습(in-sample ΔE 8.976)해서 `hasselblad.json`을 v1.3으로 갱신했다.
`raw_calib_cache/`에 챠트 2장(`x2dii-chart-31325`/`31330`)을 정식으로
추가해서 이후 모든 기본 캘리브레이션(`--cache-dir` 생략 시)이 자동으로
15쌍을 쓰게 했다 - 나머지 챠트 7장(같은 버스트라 정보량이 거의 없다고
판단해 제외)은 이슈 #4의 "다양한 실제 장면" 요청이 충족되면 재검토.

**시도했지만 채택 안 한 것**: RBF(Radial Basis Function) 기반 비선형
컬러 매칭(`ethan-ou/camera-match` 스타일, 3x3 선형 매트릭스 대신
scipy의 thin-plate-spline RBF로 raw_baseline을 대체)도 시도했다.
매트릭스와 RBF 결과를 픽셀 단위로 블렌딩(ratio=RBF 비중)해서 13-fold
LOO로 검증한 결과, ratio≈0.25에서 +1.5% 개선(9.933, 기준 10.082) -
Gray Edge+챠트pooling(+11.1%)보다 훨씬 작고, scipy를 새 의존성으로
추가해야 해서(이 모듈들은 지금 numpy만 쓴다는 원칙이 있음) 채택하지
않음. 참고로 순수 RBF(블렌드 없이 매트릭스를 완전히 대체)는 -10~13%로
오히려 더 나빴다 - 이미 잘 맞는 "쉬운" 사진(폴드별 ΔE 2.5~5대)에서
크게 나빠지고 원래 안 맞던 "어려운" 사진에서만 좋아지는 패턴이었는데,
이건 세션 초반에 시도한 픽셀 단위 gradient-boosting 회귀(scikit-learn
HistGradientBoostingRegressor)에서도 똑같이 나타난 패턴이다(그 실험도
LOO 기준 -4.7%~-5.0%로 기각) - 유연한/비파라메트릭 모델을 이 정도
규모(13~15장)의 데이터셋에 그대로 적용하면 "이미 쉬운 장면"을 희생해서
"어려운 장면"만 잡는 쪽으로 수렴한다는 게 서로 다른 두 기법(gradient
boosting, RBF)에서 일관되게 재현된 셈 - 우연이 아니라 이 데이터 규모/
다양성에서 구조적으로 나타나는 현상으로 보인다.

**"9→7" 목표 진행 상황**: 공식 벤치마크 기준 v1.2의 9.687(교차검증)에서
출발해, 이번 v1.3의 LOO 교차검증 개선폭(+11.1%)을 그대로 적용하면
대략 8.6 안팎으로 추정된다(정확한 새 공식 수치는 15쌍 전체 재교차검증이
필요 - 다음 세션 과제). 여전히 목표(7)에는 못 미치지만, 이번 세션에서
나온 유일하게 5% 기준을 넘긴 실개선이라는 점에서 지금까지의 "전부
9.4~9.7에 수렴"이라는 결론을 처음으로 깬 결과다.

**후속 실측 20(2026-07, docs/superpowers/specs/2026-07-23-matrix-features-design.md):
root-polynomial feature + 가중 최소자승(WLS)/ridge 확장 - 기각.**
`fit_color_matrix()`를 확장해서 (1) root-polynomial feature(Finlayson
2015, [r,g,b,sqrt(rg),sqrt(rb),sqrt(gb)] 6항, 노출 불변) (2) 밀도
기반/채도 기반 WLS (3) ridge 정규화를 지원하게 만들고, `feature_set x
weight_scheme x ridge` 50개 조합을 `calibrate_profile.py --mode
matrix_features`로 4-fold 스크리닝 후 1등만 15-fold leave-one-out으로
확정 검증했다(Phase 0 매트릭스 단독 비교 - 전체 파이프라인 재학습은
안 함).

| 조합 | LOO 교차검증 ΔE00 | 변화 |
|---|---|---|
| 기준선(선형, 가중치 없음, ridge=0, in-sample) | 8.284 | - |
| **1등: linear / none / ridge=0.0** | 8.713 | -5.2% |

5% 배포 기준을 못 넘겨서 `hasselblad.json`은 바꾸지 않는다. 표의
-5.2%는 새 feature/가중치가 손해를 냈다는 뜻이 아니라는 점을 짚어야
한다 - 1등 조합 자체가 기존과 동일한 `linear/none/ridge=0` 설정이라,
이 -5.2%는 "같은 모델의 in-sample vs LOO 일반화 격차"일 뿐이다(공정한
"새 축이 도움이 됐는가"는 각 조합의 CV 손실끼리 비교해야 하고, 그
기준으로는 1등 조합이 기준 대비 ~0%). 새 축 두 개(feature 확장,
재가중치) 자체가 전부 CV 기준으로 기준선보다 나빴다는 게 진짜
기각 근거다(아래). 50개 조합 중 4-fold
스크리닝 1등이 하필 `linear / none / ridge=0.0` - 즉 root-polynomial도
WLS도 ridge도 전혀 적용하지 않은, 사실상 기존 매트릭스와 동일한
설정이었다는 점 자체가 결론을 말해준다: 픽셀 가중치(density/chroma_p0.5
/chroma_p1/chroma_p2)는 예외 없이 걸수록 더 나빴고(-5.7% → -7.2% →
-9.7% → -14.3%/-14.8%, chroma는 p가 커질수록 단조 악화, density가
가장 나쁨), root-polynomial 6항 확장도 같은 weight_scheme 기준으로
매번 linear보다 나빴다(예: none 기준 -5.7% vs -8.9%, chroma_p2 기준
-14.8% vs -22.5%) - ridge 값(0.0001~0.1)은 어느 조합에서도 CV ΔE를
유의미하게 바꾸지 못했다(9개 자유도짜리 3x3 행렬이 15쌍 데이터로 이미
잘 조건화돼 있어 정규화가 할 일이 없었던 것으로 보임). 결국 이번
그리드서치의 두 축(feature 확장, 재가중치) 모두 이 데이터 규모(15쌍)
에서는 신호보다 잡음을 더 많이 끌어들였다는 결론이고, 이는 후속
실측 19의 RBF/Huber/gradient-boosting 기각 패턴("유연한 모델을
15장 규모에 그대로 적용하면 손해")과 궤를 같이한다.
`fit_color_matrix()`의 확장 자체(feature_fn/weights/ridge 인자)는
코드에 남겨둔다 - 향후 issue #4의 새 데이터가 들어왔을 때 재시도할 수
있는 도구로 남기는 것이 이 프로젝트의 문서화 철학과 일치한다.

**추가(2026-07-23): 오픈소스 레포 리서치로 나온 다른 feature 확장도
같은 패턴으로 기각.** `agfianf/color-correction`(ColorChecker 24패치
기반 색보정 라이브러리) 리서치로 그 프로젝트가 "polynomial" 모델을
root-polynomial이 아니라 sklearn `PolynomialFeatures(degree=2~3)` +
`LinearRegression`(순수 제곱항 포함 완전 다항식, 그 프로젝트는
degree=3을 기본값으로 권장)으로 구현한다는 걸 확인하고, 이 축도
시도했다. 이론적으로 불리할 거라 예상한 이유: root-polynomial(Finlayson
2015)이 제곱근 교차항을 쓰는 핵심 이유가 노출(밝기) 스케일 불변성인데
(사진 전체가 k배 밝아져도 매트릭스가 그대로 유효), 순수 제곱항(r²
등)은 k²배로 스케일돼서 이 불변성이 깨진다 - 그런데 이 프로젝트의
캘리브레이션 페어들은 사진마다 절대 노출이 10배 넘게 벌어진다
(normalize_exposure=False로 그 관계를 일부러 보존함, 후속 실측 6).

| 매트릭스 feature | in-sample(15쌍) | LOO 교차검증(15-fold) |
|---|---|---|
| 선형(기존, 3항) | 8.284 | 8.713 |
| root-polynomial(6항, 이미 기각) | 8.164 | 8.876 |
| **full polynomial degree=2(9항, agfianf 스타일)** | **8.023(가장 좋아 보임)** | **8.713(선형과 완전 동률)** |
| full polynomial degree=3(20항, agfianf 권장 기본값) | 8.204 | (in-sample부터 이미 degree=2보다 나빠서 CV 안 돌림) |

in-sample로는 degree=2가 넷 중 가장 좋아 보였지만(8.023), LOO에서는
기존 선형과 소수점까지 완전히 같은 값(8.713)으로 수렴했다 - 폴드별
편차를 보면 이유가 분명하다(15개 중 6개 폴드는 선형보다 훨씬 나음,
나머지 상당수는 훨씬 나쁨 - 평균에서 서로 상쇄). "in-sample에서
좋아 보였다가 CV에서 사라지는" 이 프로젝트의 반복되는 패턴이 이번엔
아예 완전한 동률로 나타난 것. 매트릭스 유연성을 늘리는 축(선형 ->
root-poly -> WLS/ridge -> RBF 블렌드 -> RBF 잔차 -> Huber -> full-poly)
전부 8번째까지 실패해서, 이 결론은 이제 거의 확정적이라고 봐도 될 듯
하다: 15쌍 데이터 규모에서는 매트릭스를 3x3(9개 자유도)보다 유연하게
만드는 어떤 시도도 득이 안 된다.

## 후속 실측 21: 카메라 네이티브 색매트릭스 + DCP 프로필 (2026-07-25)

**동기**: 후속 실측 9에서 차트로 피팅한 매트릭스가 libraw 기본 디코드의
색채측정 오차를 7.58 -> 2.78로 줄였지만, 그 매트릭스는 Lightroom/ACR에
넣을 수 없는 형태였다. `decode_raw()`가 `output_color=sRGB` +
`use_camera_wb=True`를 쓰므로 libraw가 **이미** 자기 색매트릭스와 WB를
적용한 결과를 다루기 때문이다 - 즉 그 매트릭스는 "libraw sRGB -> 참값
sRGB" 보정이고, DCP의 `ColorMatrix1`이 요구하는 "XYZ(D50) -> 카메라
네이티브 RGB"가 아니다. 그 자리에 넣으면 Lightroom이 다른 공간의 값으로
해석해 조용히 틀린 색을 낸다.

**방법**: `decode_raw_native()`(`output_color=raw` + `user_wb=[1,1,1,1]`)로
libraw의 색변환·WB를 둘 다 우회한 카메라 네이티브 RGB를 얻고, 그 공간에서
차트 24패치 vs XYZ(D50) 참조값으로 3×3을 피팅했다. 데이터는 후속 실측 9와
같은 X2D II ColorChecker 차트 10장.

libraw 내장 `rgb_xyz_matrix`의 방향(XYZ->cam / cam->XYZ)과 벡터 규약
(행/열)은 문서로 단정할 수 없어 네 후보를 전부 적용해 비교했다:
`M` ΔE00 46.69, `inv(M)` ΔE00 23.41, `M.T` ΔE00 42.02,
`inv(M).T` ΔE00 7.81 -> **`inv(M).T`** 채택.

> **정정(2026-07-25, 최종 리뷰 이후)**: 이 절은 처음에 `M`/`inv(M)` 두
> 후보만 시험해서 libraw ΔE00을 23.41, 개선폭을 87.9%로 잘못 기록했었다.
> libraw의 `rgb_xyz_matrix`가 DNG `ColorMatrix1`과 같은 **열벡터** 규약인데
> 이 프로젝트의 `apply_color_matrix()`는 **행벡터**로 적용하기 때문에,
> 올바른 비교를 하려면 전치한 `M.T`/`inv(M).T`도 후보에 넣어야 했다. 같은
> 실수가 `.dcp`에 쓴 `ColorMatrix1`에도 있었다(전치 누락) - 아래 결과와
> 판정은 네 후보 전부를 실측 재비교하고 `.dcp`를 재생성한 뒤의 수치다.
> 상세 유도는 `core/dcp_export.py`의 `write_dcp` docstring 참고.

**알려진 한계**:
- **장면 조명 복원 불가**: 기여받은 manifest의 `illuminant` 칼럼이 10장
  전부 비어있다(이슈 #4에서 "measured illuminant"를 요청했으나 그 항목은
  오지 않았다). 게다가 `reference_patches_xyz_d50()`이 참조값을 D50으로
  색순응시킨 뒤 피팅하므로 매트릭스는 **구성상** D50 기준이고, 촬영 당시
  장면 조명은 이 데이터에서 **복원 불가능**하다. 그래서
  `CalibrationIlluminant1`은 매트릭스가 실제로 대응하는 참조 백색점인
  **23(D50)**을 쓴다 - 장면 조명을 측정/가정한 값이 아니다.
  `AsShotNeutral` [0.3688, 1.0000, 0.5917]에서 CCT를 역산하는 접근은
  무효로 판명됐다(진단으로만 남김): `AsShotNeutral`과 무채색 패치에서
  실측한 네이티브 중립색 [0.4094, 1.0000, 0.4940]이 채널별로
  R×1.110/B×0.835만큼 어긋나(스케일 규약이 다름), 그 역산 xy/CCT는
  의미가 없다.
- **조명 조건 1개**: 10장 전부 94초 한 버스트라 dual-illuminant 보간이
  불가능하다(`ColorMatrix2` 미사용).
- **Lightroom 렌더링 미검증**: 생성 파일의 TIFF 구조 유효성(exiftool
  파싱)과 수치 라운드트립은 검증했지만, Lightroom/ACR이 실제로 로드해서
  의도한 색을 내는지는 개발 환경에 Adobe 제품이 없어 확인하지 못했다.
- **`ForwardMatrix1` 미포함**: DNG 스펙상 카메라 중립점을 D50 백색점으로
  정확히 매핑하는 정규화 제약이 있는데 그 구현을 검증할 방법이 없어
  넣지 않았다(`ColorMatrix1`만 있는 프로필도 유효). `write_dcp()`는
  옵션 인자로 지원한다.
- **패치 24개 / 카메라 1대**: ColorChecker Classic(무채색 6 + 유채색 18)은
  본격 프로파일링 타깃보다 훨씬 적어 차트에 없는 색역의 정확도는 알 수
  없고, X2D II 100C 전용이다(`UniqueCameraModel`로 대상 명시).

**기존 `raw_baseline_matrix`와의 관계**: 이 매트릭스는 `hasselblad.json`의
`raw_baseline_matrix`를 대체하지 않는다. 그쪽은 "카메라 JPEG 룩 근사"가
목적이고(후속 실측 9에서 확인: 차트 참값에 대고 재면 오히려 나빠지는 게
정상), 이쪽은 색채측정 정확도가 목적인 별개 산출물이다. `hasselblad.json`은
건드리지 않았다.

## HNCS 구조 실험: 4단계 구조 미러링이 ΔE를 개선하는가

**배경**: `apply_hncs()`(Stable)는 실제 HNCS 파이프라인을 3단계로
단순화한 근사다. 실제 구조(조명별 매트릭스 -> 조명별 chroma LUT ->
공유 필름커브, `docs/hncs_structural_research.md` 참고)를 미러링한
연구용 실험 모듈(`hybrid_engine/research/hncs_structural.py`)이 실제로
ΔE를 개선하는지 leave-one-out 교차검증(13쌍, `tools/evaluate_hncs_structural.py`)으로
측정했다.

**결과** (같은 13쌍, CIEDE2000, held-out마다 재피팅):

| 방법 | 평균 ΔE (CIEDE2000) |
|---|---|
| `apply_hncs()` (raw 기반 baseline에 적용, 이 실험 안에서 재측정) | 10.629 |
| 구조 실험 (`apply_hncs_structural`, 클러스터별 매트릭스+chroma LUT+공유 필름커브) | 10.191 |

개선폭: 4.1% (구조적 실험이 이겼다)

**측정 방식 참고**: `tools/evaluate_hncs_structural.py`는 그리드서치를
폴드당 수백 번 반복해야 해서 `apply_hncs_structural()`을 raw 경로마다
직접 호출하지 않는다 - 대신 다운샘플된 캐시 위에서 같은 4단계
시퀀스(매트릭스 -> chroma LUT -> 공유 필름커브, 같은 상수)를
`structural_delta_e()`/`fit_chroma_lut_params()` 안에 인라인으로
적용한다. `apply_hncs_structural()`과 동일한 순서/상수를 쓰므로 현재는
수치상 동등하지만, 둘 중 하나만 수정하면 이 표의 10.191이 더 이상
`apply_hncs_structural()`이 실제로 내는 값과 일치하지 않게 될 수
있다는 점은 알아둘 것.

**판정**: 구조 실험이 근소하게 이겼다 (4.1% 개선, 13쌍 중 6쌍에서 우세,
7쌍에서 열세) - 평균은 이겼지만 폴드 과반(7/13)에서는 오히려 졌다,
실재하지만 좁고 일관되지 않은 효과이지 결정적 승리가 아니다. 폴드별로
보면 `cluster_b`(소수 클러스터, 3쌍)에서는 결과가 엇갈렸다
([x1d-II-sample-09.jpg]는 구조 실험이 5.249 vs 13.449로 크게 이겼지만,
[B0000994.jpg]와 [02709.jpg]는 반대로 졌다) - 아래 "알려진 한계"의
`cluster_b` 표본 부족과 무관하지 않을 것이다.

**알려진 한계**:
- **표본 13쌍, 클러스터당 3~10쌍(소수 클러스터 3쌍)** - 통계적으로
  매우 얇다. 특히 `cluster_b`(3쌍)는 leave-one-out 시 학습 데이터가
  2쌍뿐이라 매트릭스 피팅이 ridge 정규화(=1.0)에 크게 의존한다.
- **DOWNSAMPLE_MAX_DIM=512로 축소한 이미지에서 피팅/측정** - 3x3
  매트릭스와 2-파라미터 chroma LUT 둘 다 공간 정보가 아니라 색 분포에만
  의존하는 전역 변환이라 실질적 영향은 작다고 보지만, 원본 해상도에서
  재측정하면 수치가 달라질 수 있다.
- **chroma LUT 그리드가 성기다**(`sat_mult` 7개 x `hue_shift_deg` 7개) -
  더 촘촘한 그리드나 연속 최적화가 이 결과를 바꿀 수 있다.
- **`apply_hncs()`를 대체하지 않는다** - 이 실험이 이겨도 Stable로
  승격하지 않는다(별도 논의).

**기존 v8~v12 RMSE 23.3과의 관계**: 그 수치는 다른 표본/다른 측정
방식(RMSE, 이 실험은 ΔE)이라 그대로 비교하지 않고, 이 실험 안에서
`apply_hncs()`의 ΔE를 같은 13쌍 raw 기반으로 재측정했다(위 표의
`apply_hncs()` 행).
